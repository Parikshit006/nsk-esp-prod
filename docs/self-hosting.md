# AWS-hosted server launch plan (provisional)

The organizer chose an AWS-hosted server, using the existing self-hosted application package. The AWS account, region, instance, domain and access are not available yet. This is an operator plan, not a declaration that the service is ready for public use. The current app has a captain result-report workflow, a synthetic recovery drill and a 12-month private-evidence deletion job, but still lacks a real server recovery exercise and production load checks. Do not accept real payments or personal data for a live tournament until those controls are complete.

## Server layout

- Use an EC2 instance with a supported Linux release, Docker Engine and Compose, an encrypted persistent EBS volume, and a separate encrypted backup destination. Pin the deployed commit and image digest. Size the instance after measuring OCR and spectator load on staging.
- Terminate HTTPS in a maintained reverse proxy. Proxy only the public origin to the app's loopback-bound port 3000. Keep PostgreSQL on a private network; the provided Compose file binds its port to loopback for local administration. Restrict SSH and host firewall access.
- Use a unique high-entropy database password, readiness token, and 32-byte room-credential encryption key. Keep them outside Git in a root-readable environment file or secrets service. Back up the encryption key separately; losing it makes room details unreadable. Rotate compromised credentials and revoke sessions as part of an incident response.
- Deploy with `docker compose up --build -d` only after setting `POSTGRES_PASSWORD`, HTTPS `WEB_ORIGIN`, `READINESS_TOKEN`, `CREDENTIAL_ENCRYPTION_KEY`, and SMTP host, port, user, password and sender address. If using Amazon SES SMTP, use its [region-specific SMTP credentials](https://docs.aws.amazon.com/ses/latest/dg/smtp-credentials.html) and a verified sender; these credentials differ from AWS access keys. Configure TLS for the chosen SMTP port and test signup verification, organizer invitations and password recovery on staging. The app image runs forward-only, checksum-protected migrations before starting. Review each migration and take a recoverable backup before an upgrade.

## Backups and recovery

Local infrastructure status (20 October 2026): the organizer has not provisioned the AWS server. Region, OS, domain and access will be supplied later. Development and deployment preparation continue locally. Compose now includes process reaping, restart policies, an authenticated readiness check, a read-only app filesystem, a bounded temporary directory and a 120-second shutdown allowance for screenshot work. The Docker engine remains unavailable locally, so these container settings still require runtime validation.

Run `pnpm ops:recovery-drill` with `DATABASE_URL_TEST` naming a database ending in `_test`. Set `PG_BIN` to the PostgreSQL 17 binary directory if its tools are not on PATH. This creates uniquely named isolated schemas, migrates them, inserts synthetic binary/encrypted/snapshot data, dumps and restores it with PostgreSQL tools, checks integrity and removes only its generated schemas. A successful run removes its temporary dump; a failed run retains it under ignored `.local/recovery-drills` for diagnosis. It never targets the configured production database. The local run passed in approximately 1.6 seconds; this is a small synthetic test, not a production recovery-time commitment. A real event restore and off-server encrypted backup exercise remain required.

The API runs a local English OCR worker with one active job per process, a 20-job pending limit, 90-second recognition timeout, leases and at most three attempts. Successful readings are reused for the same evidence. Original images and readings remain private to admins. Allow CPU and memory headroom and measure representative jobs before selecting the server size. Derived text is also personal data and must be included in retention policy implementation.

The API also checks for due room releases every 15 seconds and writes one in-app notice for each currently eligible captain or linked player. A database marker prevents duplicate release notices across app replicas. The notice contains no room ID or password; recipients open protected match access to view them. Monitor the app error log for failed checks, since email and push alerts are not configured.

The evidence-retention worker starts after the API and checks once a day. It processes up to 50 due tournaments per pass. Monitor `evidence_retention_failed` and `evidence_retention_purged` events; a failure requires investigation and a successful later pass. The first pass begins one minute after startup. To inspect or run it manually, use `pnpm ops:retention --preview` or `pnpm ops:retention` with the protected `DATABASE_URL`. In Docker, use `docker compose run --rm --no-deps app node apps/api/dist/apps/api/src/evidence-retention-cli.js --preview` and omit `--preview` to execute it. Confirm the normal app is running first so its migrations have completed.

## Room encryption-key rotation

Take a verified encrypted backup and retain the old key separately. Use a maintenance window with app writes stopped: old app processes cannot decrypt rooms created by a new key. Stop only the app (`docker compose stop app`), leaving the database running. Set `CREDENTIAL_ENCRYPTION_KEY` to a fresh 64-hex-character key and `CREDENTIAL_ENCRYPTION_KEY_PREVIOUS` to the old key in the protected Compose environment. Run `docker compose run --rm --no-deps app node apps/api/dist/apps/api/src/rotate-credential-key-cli.js`. The tool updates every saved room version in one database transaction, verifies each converted value, and rolls back if a key or record is wrong. It is safe to rerun; a successful second run reports zero conversions. Remove the previous key from the environment, start the app, and verify protected room access with a test account before reopening traffic. Retain the old key with the pre-rotation backup for its backup lifetime. Rehearse this procedure on staging before production use.

1. Take an encrypted PostgreSQL custom-format backup at least daily and before each deployment. The private payment and result images are stored in PostgreSQL, so they are included. Keep a separate encrypted off-server copy and a record of backup completion.
   EBS snapshots can supplement this database backup but should not replace the tested PostgreSQL restore procedure. [AWS does not automatically create EBS backups](https://docs.aws.amazon.com/ebs/latest/userguide/ebs-snapshots.html); configure and verify an AWS Backup or snapshot schedule for the instance's persistent volume.
2. Keep a rolling 30-day backup set as a provisional operating choice. The final schedule must account for any longer legal hold and for the deletion policy below. Do not leave decrypted exports in shared folders.
3. Test a restore into an isolated database at least monthly. Verify migration level, row counts, a sample event's published result and podium, and decryption of a test room credential using the separately stored key. Record elapsed recovery time; choose an RTO from this measured result.
4. During an incident, stop writes, preserve the affected database and logs, restore to a clean environment, verify the private key and evidence hashes, then reopen traffic. Never restore an old dump over the only current copy.

For a Docker installation, a backup command run on the host can be `docker compose exec -T db pg_dump -U esp -d esp -Fc > /secure-backups/esp-YYYYMMDD.dump`. Protect and encrypt the output at rest and in transfer. Perform restores in a separately named database first; `pg_restore` must target that isolated database. Test these commands on the actual server before relying on them.

## Capacity check and provisional target

Run `pnpm ops:load-check` with `DATABASE_URL_TEST` ending in `_test`. It creates a disposable isolated schema and requests public event list, detail and configuration pages 600 times with 30 concurrent clients. On this development machine, the check returned 0 errors, 100 ms median, 257 ms p95 and 448 ms p99 (20 October 2026). These are local reference numbers, not server capacity. A provisional launch target is under 1% error rate and under 500 ms p95 for these public reads at the expected peak concurrency; establish the actual peak and repeat the check against staging with realistic event and standings data. Also measure uploads, OCR queue delay, database size and backup/restore duration before choosing the server size and an operational recovery target.

## Suggested evidence retention for organizer review

**Organizer-approved operating period:** retain private payment-proof images, original match screenshots, captain report screenshots and OCR text for 12 months after tournament completion or cancellation. The daily job erases those image bytes and OCR output after that date, while preserving the hashes, result decisions, standings and audit history. It waits while refund reviews or result reports are open. A super admin can place or release a reasoned legal hold in the event's admin workspace; both actions are audited. Reopening a completed event clears its deletion date until it is finalized again. Copies in the rolling backup set age out according to the backup schedule. Metadata, logs and public rankings need their own published retention policy and legal review.

This selected period is not a statutory retention determination. India's [Digital Personal Data Protection Rules, 2025](https://www.meity.gov.in/static/uploads/2025/11/53450e6e5dc0bfa85ebd78686cadad39.pdf) include a one-year minimum for covered processing data and logs in Rule 8(3), while [the commencement notification](https://www.meity.gov.in/static/uploads/2025/11/c56ceae6c383460ca69577428d36828b.pdf) phases in the underlying Act. Rule 8 is scheduled to take effect eighteen months after the November 2025 publication. The [Act's erasure provision](https://www.meity.gov.in/static/uploads/2024/02/Digital-Personal-Data-Protection-Act-2023.pdf) also allows retention where needed for a specified purpose or another law. Whether those provisions and any payment, tax, or gaming-specific rules apply to each record needs local legal review before real-event launch.
