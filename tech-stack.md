# 2. How the work is split: three modes of building

Your plan has three different ways of producing code. Naming them keeps expectations honest.

| Mode | Applies to | Who writes | Human involvement |
|---|---|---|---|
| **A. Learn-then-write (manual)** | The whole Node/Express backend, SQL, auth, queues, scoring, identity matching | You create every file; AI writes code only after you can explain the concept; you read and paste | Full |
| **B. Agent-generated (Antigravity)** | React frontend | Claude Opus 4.6 in Antigravity | Prompts, contracts, review of results |
| **C. Hybrid** | Tests, Docker/CI config, OCR worker, OpenAPI | AI drafts, you review | Review and run |

## 2.1 Honest assessment of the plan

**Backend plan: good fit, with two additions.**
- It matches the project's nature. The backend holds the parts where correctness matters most (state machines, scoring, access control, audit). Writing it by hand while learning is the right place to spend your attention.
- *Addition 1: write the tests yourself first for the scoring and state-transition modules.* They are small, deterministic, and teach the domain rules (`problem.md` §19, §25). Letting AI write the implementation after you write the test is a strong learning loop.
- *Addition 2: keep a one-line "why" for every file in your own notes.* It is the cheapest way to verify you actually learned the concept rather than only pasted it.

**Frontend plan: workable, but not "blind" in practice.** Fully hands-off generation works best when the agent is tightly constrained. The risk is not visual quality; it is that the frontend can quietly encode wrong assumptions: showing unverified data as official, hiding but not protecting credentials, or letting an admin screen submit stale edits. The most important screen, the **OCR review screen (F15)**, is also the one where speed and clarity decide whether the five-minute objective is achievable. So:
1. Give the agent a **contract**, not a vague description: the OpenAPI spec, the state tables from `problem.md` §25, and the feature text for the exact `F` item.
2. Give it **rules** (§8.3 below): the frontend never decides authorization, never computes scores, and shows only API data.
3. Verify with **Playwright end-to-end tests** (written by you or by the agent, but run by you), and personally walk through the review screen with real screenshots before trusting it.

This keeps the frontend hands-off for code but not for outcomes. Your backend is the source of truth, so a frontend bug cannot create official data (D1, D10).

**One flag on the plan:** several AI-generated frontend features depend on backend endpoints that do not exist yet. Build backend slices first (or at least the contract), then prompt the frontend slice. Reversing the order tends to produce invented endpoints.

# 3. Backend

## 3.1 Language: TypeScript vs. JavaScript

| Option | For | Against |
|---|---|---|
| **TypeScript (recommended)** | Types catch whole classes of state and data-shape errors (this project has many states and statuses); contracts shared with the frontend through `packages/shared`; better AI-assisted refactoring | Extra concepts to learn; build step |
| Plain JavaScript | Less to learn, closer to "revise Node" | Easier to ship subtle shape bugs; no shared compile-time contracts |

**Recommendation:** TypeScript with `strict` on, but you may start a module in JS if you want to focus on the Node concept itself; convert later. Use `tsx` for running in development and compile with `tsc` for production.

## 3.2 Runtime and framework

- **Node.js Active LTS.** Node's release policy is moving to one major per year with every release becoming LTS starting with Node 27; Node 24 is currently Active LTS, and Node 26 is scheduled to enter LTS in October 2026 (Node.js release working group announcements, checked 2026-10-18). Use 24 now; move to 26 once promoted. Pin the version in `.nvmrc` and `engines`.
- **Express 5.** Matches your chosen framework. Concepts you will revise or learn: routing, middleware chain, error-handling middleware, request lifecycle, async handlers.
- Alternatives (not chosen, as Express was your request): Fastify (faster, schema-first), NestJS (structured but heavier). Revisit only if Express becomes a limit.

**Internal structure (conceptual, to be formalized in `architecture.md`):** `routes → controllers → services → repositories`, with **state-transition and scoring logic as pure functions** in a `domain/` folder with no Express or database imports. This is what makes scoring "deterministic and independently testable" (D8, §19.5).

## 3.3 Database: PostgreSQL

**Why PostgreSQL suits this project** (reasons drawn from `problem.md`):
- **Transactions and constraints** enforce BR-S1 (one team per slot), BR-R2, BR-X9 (one active result per attempt), and the idempotency requirements (EX-08, ER-09R).
- **Partial unique indexes** express rules such as "one *active* registration per team per tournament" directly in the database.
- **Row locking** (`SELECT … FOR UPDATE`) prevents two admins assigning the same slot (ES-01).
- **JSONB** stores raw OCR output (boxes, confidences) without forcing an early schema.
- **Append-only audit** can be protected with permissions and triggers.
- **Unicode:** use UTF-8 database encoding; store raw IGNs untouched; derived normalized forms in separate columns (D4, §17.2).
- **Extensions worth evaluating (proposal):** `pg_trgm` (trigram similarity as a *candidate-generation* aid, never a final match), `citext` or ICU collations for case-insensitive comparison of normalized team names. Application-level matching remains the source of truth for identity decisions.

**Access layer: Drizzle ORM (recommended) vs. alternatives**

| Option | For | Against |
|---|---|---|
| **Drizzle ORM + drizzle-kit** | Thin and SQL-shaped, so it helps you *learn SQL*; supports partial indexes and constraints in its schema; migrations are plain SQL you can edit | Younger ecosystem |
| Prisma | Excellent developer experience, large community | Abstracts SQL more; partial unique indexes and some constraints need hand-written SQL migrations |
| Kysely or `pg` + SQL | Maximum control and learning | More boilerplate; no schema-driven migrations by default |
| Knex | Familiar, mature | Weaker typing |

Whichever is chosen, important integrity rules (uniqueness, check constraints, foreign keys, immutability triggers) belong in **SQL migrations**, not only in application code.

**Database practices:**
- Migrations are versioned and reviewed; never edit applied migrations.
- Every mutable entity carries a `version` (optimistic concurrency, BR-X10) and timestamps.
- Soft-retire evidence; never `DELETE` it (BR-X8).
- Backups: automated dumps or the host's point-in-time recovery; rehearse a restore before the first real tournament (§29.6). RPO/RTO targets need owner input (§24).
- Local development: PostgreSQL in Docker Compose, with a separate test database.

## 3.4 Validation and API contract

- **Zod** schemas for every request and response, located in `packages/shared`, used by Express middleware on the backend and for typed API calls on the frontend.
- **OpenAPI** generated from the Zod schemas (e.g., via `zod-to-openapi` or an equivalent), served for reference and handed to Antigravity as the frontend contract.
- Style: REST/JSON under `/api/v1`; consistent error shape with machine-readable codes (e.g., `STALE_VERSION`, `NOT_ELIGIBLE`); **idempotency keys** on state-changing requests (approve, upload, publish).
- No API route lists in this document; those belong in `api-specification.md`.

## 3.5 Authentication and authorization

| Concern | Proposal | Notes |
|---|---|---|
| Sessions | **Server-side sessions stored in PostgreSQL** (e.g., `express-session` + `connect-pg-simple`), HTTP-only, Secure, SameSite cookies | Revocable instantly (needed for compromised admin, EX-11). JWT is not chosen: revocation is harder and you gain nothing here. |
| Password hashing | **Argon2id** (`argon2` package) | |
| Login method | **Email + password** as a baseline; phone/OTP or college SSO deferred | `problem.md` leaves the method open (A-05, F2). |
| CSRF | SameSite cookies plus a CSRF token on state-changing requests | |
| Authorization | Role and tournament-scope checks in middleware **plus object-level checks in services** | Never rely on hidden UI (ideation §5). Covers EX-01…EX-05. |
| Rate limiting | `express-rate-limit` on login, uploads, disputes | |
| Headers | `helmet`, strict CORS (allow only the web origin) | |
| Secrets | Environment variables, `.env` files git-ignored, validated at startup with Zod | |

## 3.6 Background jobs and OCR processing

OCR must not run inside an HTTP request (it can be slow, fail, or time out, ER-02R). Proposal:

- **pg-boss**: a job queue that lives in PostgreSQL. Reasons: no extra infrastructure (no Redis), transactional enqueue (a job and its evidence row commit together), built-in retry, expiry, and deduplication keys that map to "idempotent per (evidence hash, attempt, pipeline version)" (§16.7).
- Alternatives: BullMQ (needs Redis; more features), simple polling table (most educational, least featureful). BullMQ is reasonable if Redis is introduced for another reason.
- Job status reaches the UI by **polling or Server-Sent Events**; WebSockets are not justified at this scale (Q-21 pending).
- Queue behavior needed (from §28.8): priority to the current match, visible backlog and ETA, bounded retries, `TimedOut` handling, manual-entry fallback when the queue is unhealthy.

## 3.7 File storage and uploads

- **Object storage (S3-compatible)** for screenshots and payment proofs: private buckets, short-lived signed links for viewing, no public URLs (§27.3).
- Development: local disk or MinIO behind the same storage interface.
- Upload pipeline: `multer` (or streaming parser) to a temporary location → **content-type detection by magic bytes** (e.g., `file-type`) → decode check and **re-encode with `sharp`** (strips metadata, defends against malformed or malicious files) → content hash (SHA-256) for duplicate detection (BR-X9, EM-10) → store original unmodified as evidence plus a derived working copy for OCR.
- Size and dimension limits; resolution warnings for low-res images (EO-05).
- Retention policy is undecided (Q-15); the storage layer must support retiring (not deleting) evidence.
- Hosting choice for object storage: S3, Cloudflare R2, or another provider, decided with budget (Q-24). An abstraction layer keeps this swappable.

## 3.8 OCR engine and identity matching (the high-risk component)

`problem.md` forbids choosing an engine without evidence (Q-08, §16.4), so the stack defines **how to choose**, not the winner.

**Architecture:** the API calls an internal `OcrProvider` interface. Providers return the same structure: text, bounding boxes, per-field confidence, provider/version. This lets you swap engines and run two for comparison (F13, FR-O4).

**Candidate providers to bake off:**

| Candidate | Runs where | Why consider | Concern |
|---|---|---|---|
| PaddleOCR / EasyOCR (Python) | Small separate **Python worker** (`services/ocr-worker`) called over HTTP or via the queue | Return boxes and confidence; local; no per-image fees | Another language/runtime to run; accuracy on stylized names unknown |
| Tesseract (Node binding such as Tesseract.js, or native) | In Node | Simple deployment | Typically weakest on stylized UI text (to be measured) |
| Managed OCR API | External | Maintained models, broad script coverage | Cost, latency, availability, data leaves your system, rate limits (R11) |
| Vision-language model as secondary reader | External | Useful on difficult crops | Can return plausible but wrong text; draft only |

Generic third-party benchmarks are not relied on (`problem.md` §33). **Bake-off method:** build the labeled screenshot corpus first (§30), run each candidate on it, and compare field-level accuracy, incorrect-match rate, latency, and cost.

**Identity matching stays in Node/TypeScript** and is deliberately *not* delegated to a model:
- Unicode normalization via the built-in `String.prototype.normalize` (NFKC and others).
- Derived forms (NFKC-folded, case-folded, confusable-skeleton) computed by your own tested code with a **controlled confusables table** (D4, §17.4–17.5).
- Weighted edit distance (own implementation or a small library such as `fastest-levenshtein` as a base) with OCR-confusion-aware costs.
- Tiered ranking with a **margin rule** (§17.5), thresholds calibrated from the corpus (Q-22).
- This is excellent learning material for you (string algorithms, Unicode) and fully unit-testable.

**Image preprocessing:** `sharp` for crop, scale, and contrast adjustments; layout-specific crop definitions configured per supported screenshot layout (Q-01, Q-04).

## 3.9 Scoring, standings, and state machines

- Pure TypeScript functions in `domain/`: `scoreMatch(verifiedData, ruleVersion, penalties)`, `rankMatch`, `computeStandings(publishedResults)`, tie-break resolution.
- **No language model touches arithmetic** (§19.5).
- State machines for tournament, registration, payment, approval, slot, match, job, identity match, result, dispute (§25) implemented as explicit transition tables; invalid transitions throw and are audited (§25.3). A library such as XState is optional; a hand-written transition map is simpler and more educational.
- Standings recompute as a transaction producing a snapshot and a rank-diff (F19, EL-07…09).
- Tests: table-driven unit tests with worked examples; property tests (e.g., `fast-check`) for "recompute twice gives the same result" (EL-09).

## 3.10 Banner (result image) generation

- Proposal: render from a **published snapshot** using **Satori** (JSX/HTML to SVG) + **resvg** (SVG to PNG), or `sharp` with SVG templates. No browser needed, runs inside Node, fast to test.
- Alternative: Playwright/Puppeteer screenshot of an HTML template (heavier, more flexible, more ops burden).
- Banner failure must never block publication (ER-06R, F20). Scope is **Validate** (ideation §7).

## 3.11 Notifications

- Core: in-app status (stored notifications, read via the API).
- External channels (email, WhatsApp, SMS) are **undecided** (Q-23, D-02). If email is chosen, use a transactional email provider via an SMTP/API adapter (e.g., Nodemailer + provider). Do not place room credentials in message bodies by default (§15.1).

## 3.12 Logging, monitoring, and errors

- **pino** structured logs with a **correlation ID per request** and per job; never log credentials, passwords, or proof content (§15.1).
- Health endpoints for API, database, queue, storage, OCR provider.
- Metrics needed by §30 (upload→draft latency, review time, upload→publish time, flagged-row share) recorded as events in the database; Prometheus (`prom-client`) or a hosted tool is optional later.
- Error tracking (e.g., Sentry) optional, subject to privacy review.

## 4.3 Architecture expectations (constraints for the agent)

1. **The frontend is untrusted.** It never decides authorization or eligibility; it displays what the API allows and handles denials (403/409) gracefully.
2. **No business logic duplication.** The frontend never computes scores, ranks, or standings. It shows server results (D8).
3. **Status clarity:** drafts, verified, and published data are visually distinct; unverified OCR data is never styled like official results (D1).
4. **Concurrency:** every edit sends the entity `version`; a `STALE_VERSION` response triggers a refresh prompt (BR-X10).
5. **Idempotent actions:** buttons disable during submission; requests carry idempotency keys (EX-08).
6. **Mobile-first and accessible:** participant pages must work well on phones (A-10); admin screens work on laptop and tablet; keyboard operation for the review screen; sufficient contrast (§24).
7. **Empty, loading, and error states** for every screen (a pattern observed on the reference site's tournament list, §6.2).

## 4.4 Prompting protocol for Antigravity

Work in **vertical slices**, each tied to feature IDs from `ideation.md`:

1. Provide (a) a repository `AGENTS.md`-style rules file with §4.3 constraints; (b) the relevant OpenAPI section; (c) the feature text (the `F` item) and its edge cases; (d) the `problem.md` state tables for that entity.
2. Ask for the slice plus its Playwright test.
3. Run the tests and click through it yourself against the real backend.
4. Only then move on.

Suggested order (follows the build order in `ideation.md` §10): auth shell and role routing → tournament public pages (F1) → registration/roster/IGN forms (F4, F5) → payment (F6) → admin queues (F7, F8, F24) → matches and credentials (F9–F11) → manual result entry and verification screen (F16, F15) → leaderboards (F18, F19) → OCR upload and review enhancements (F12–F15) → disputes, banners (F22, F20).

**Do not ask the agent to invent endpoints.** If a needed endpoint is missing, add it to the backend contract first.

# 8. Learning plan for the hand-written backend (Mode A)

1. Create the file and write one sentence: *what is this file's job?*
2. Ask yourself: do I know the concept? Try to explain it without help.
